# 구단별 찜 컬렉션과 일정 생성 흐름

## 사용자 흐름

1. 사용자가 홈 콘텐츠나 지도 검색 결과를 찜한다.
2. 장소 지역과 경기장 정보를 기준으로 적합한 구단 컬렉션을 기본 제안한다.
3. 사용자는 제안을 바꾸거나 새 컬렉션을 만들 수 있고 같은 장소를 여러 컬렉션에
   저장할 수 있다.
4. 경기 선택 후 관련 컬렉션을 불러올지 확인하고, 불러온 목록에서 이번 여행에
   사용할 장소를 선택한다.
5. 도착지·경기장 주변 추천 목록에서 선택한 장소도 같은 여행 후보에 합친다.
   홈·지도에서 특정 여행에 바로 추가한 장소도 같은 후보다.
6. 꼭 가고 싶은 후보는 필수 방문으로 설정한다.
7. 알고리즘은 필수 후보, 일반 후보를 먼저 배정하고 이후 빈 시간에 자동 추천을
   추가한다.
8. 생성 후 사용자는 순서를 바꾸거나 Item을 고정한다. 재생성은 고정되지 않은
   Item만 재배치·교체한다.

## 개념 구분

| 개념 | 저장 시점 | 의미 |
| --- | --- | --- |
| 찜 | 여행 전 | 나중에 보고 싶은 장소 |
| 여행 후보 | 생성 직전 | 이번 여행 알고리즘에 전달할 장소 |
| 필수 방문 | 생성 직전 | 날짜·순서는 바뀌어도 반드시 포함할 장소 |
| 일정 고정 | 생성 후 | 재생성해도 현재 날짜·순서를 유지할 Item |

## Firestore 초안

```text
users/{userId}/favoriteCollections/{collectionId}
  name
  teamId nullable
  stadiumIds[]
  regionCodes[]
  createdAt
  updatedAt

users/{userId}/favoriteCollections/{collectionId}/items/{placeId}
  placeId
  createdAt
```

장소 이름·주소·이미지는 컬렉션에 복제하지 않고 `places/{placeId}`를 조회한다.
`items`의 문서 ID를 `placeId`로 사용하여 컬렉션 내부 중복을 막는다.

이번 여행 후보는 컬렉션과 별도로 저장한다.

```text
trips/{tripId}/placeCandidates/{placeId}
  placeId
  isRequired
  createdAt
  updatedAt
```

컬렉션에서 불러오기, 주변 추천에서 선택, 홈·지도 직접 추가는 모두 같은 후보
문서를 만든다. 유입 경로는 일정 생성 규칙에 영향을 주지 않는다.

## 생성 및 재생성 우선순위

```text
Anchor
→ 고정 Item(재생성일 때)
→ 필수 방문 후보
→ 일반 사용자 선택 후보
→ 알고리즘이 추가하는 추천 장소
```

필수 장소라도 경기장 40분 전 도착, 출발지 1시간 전 도착, 영업시간과 입장 마감
제약을 위반하면서 강제로 넣지 않는다. 가능한 일정은 반환하고 필수 장소 충돌을
프론트가 분명히 알 수 있게 표시한다.
