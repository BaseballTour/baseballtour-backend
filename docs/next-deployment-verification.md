# 다음 작업으로 이관 — 배포 후 실제 서버 검증

이번 작업에서는 자동 테스트와 로컬 Firestore·TourAPI 검증까지 수행했다. PR #66
병합, Cloud Run 재배포 및 실제 사용자 데이터를 변경하는 검증은 다음 작업으로
이관한다.

## 배포 확인

1. PR #66이 `main`에 병합됐는지 확인한다.
2. Cloud Run 리비전의 `commit-sha`가 병합 커밋인지 확인한다.
3. `TOUR_API_PERSISTENT_CACHE_ENABLED=true`인지 확인한다.
4. Firestore `tourApiResponseCache` 컬렉션과 `expiresAt` TTL 정책을 확인한다.

## TourAPI 확인

1. 같은 주변·상세 조회를 두 번 수행한다.
2. 첫 요청의 `miss/stored`, 두 번째 요청의 `hit` 로그를 확인한다.
3. 제공기관 상태 확인은 캐시를 우회한 진단 명령으로 별도 수행한다.
4. timeout·호출 제한 응답이 캐시에 저장되지 않는지 확인한다.

## 사직 추천 품질

실제 Kakao 경로가 적용된 사직 1박 2일 일정을 생성해 날짜별 추천 수,
식사 시간대, `travelTimeSource`, 제외 사유를 확인한다. 실제 경로에서도 추천이
적을 때만 사직 후보 반경이나 시간대별 후보 선별을 조정한다.

## 실제 사용자 통합 흐름

테스트 계정으로 찜 저장 → 경기 지역 Import → 필수 여부 변경 → 일정 생성 →
자동 추천 고정 → 재생성 → 날짜·시간·순서 편집을 수행한다. 각 단계에서 API
응답, 일정 상세 조회, Firestore 문서가 동일한지 확인한다.
