- 경기장과 같은 장소 및 스포츠 시설 제외
- 숙박 후보 제외
- 카테고리별 상한 적용

품질 개선이 필요한 부분:

1. 경기일 균형 배정 보완 후 네 지역 모두 경기 당일 자동 추천이 1~3개 들어갔다.

   따른 차이는 남아 있다.
2. `UNPARSABLE`, `MISSING` 영업시간은 알고리즘 제약에 사용하지 않고 원문 또는 `운영시간 확인 필요`로 표시해야 한다.
3. 잠실은 음식점 비중이 높고 사직은 쇼핑 후보가 없었다. 지역별 원천 데이터 차이를 고려해 카테고리 최소 다양성 정책을 검토한다.

## 3. 외부 API 호출량과 성능

### TourAPI

- 주변 조회는 지역당 1회다.
- 상세 후보 하나마다 공통·소개·이미지 API를 각각 호출한다.
- 최초 조회 총 호출은 잠실 31회, 고척 46회, 사직 34회, 대전 37회였다.
- 같은 조건을 다시 조회하면 Adapter 캐시로 실제 외부 호출은 네 지역 모두 0회였다.
- 새 인스턴스에서도 재사용할 수 있도록 원본 성공 응답을 Firestore
  `tourApiResponseCache`에 저장한다. 상세 응답은 12시간, 검색 응답은 30분
  유효하며 API 키는 저장하지 않는다.
- 로컬의 새 프로세스 검증에서 상세 응답은 약 187~219ms에서 16~31ms로
  감소했다. 키워드 검색은 당시 일일 한도 초과였으므로 저장되지 않았다.
- 키워드 검색 성공 결과는 30분 캐시하고, 동시 동일 요청은 한 번으로 합친다.
- 동일 키워드 요청에서 호출 한도 초과가 발생하면 60초 동안 외부 재호출을 막는다.
- 현재 상세 fan-out은 최초 후보 수에 비례한다. 공유 캐시로 반복 호출은 줄였지만
  처음 보는 장소의 상세 조회 동시성 제한과 필요한 후보만 상세화하는 최적화는
  후속 과제로 남긴다.

### Kakao 경로 Matrix

- 작은 실제 Matrix의 최초 생성: 0.824초, Kakao HTTP 28회
- 같은 Matrix 재생성: 0.001초, Kakao HTTP 0회
- 성공 경로뿐 아니라 최근 실패 경로도 60초 캐시하도록 보완했다.
- 최초 결과는 Kakao 4개, 직선거리 추정 16개였다. 실패 경로는 `ESTIMATED`로 유지돼 전체 일정 생성은 중단되지 않는다.

## 4. 장애 시나리오

| 상황 | 기대 결과 | 검증 |
| --- | --- | --- |
| TourAPI timeout | HTTP 503, `EXTERNAL_API_TIMEOUT` | 자동 테스트 완료 |
| TourAPI HTTP 429 | HTTP 429, `EXTERNAL_API_RATE_LIMITED` | 자동 테스트 완료 |
| TourAPI 업무 호출 제한 코드 | 429와 같은 오류 매핑 | 기존 자동 테스트 완료 |
| 빈 정상 응답 | 성공 및 빈 목록 | 자동 테스트 완료 |
| 일부 장소 좌표·필수값 오류 | 해당 장소만 제외하고 나머지 유지 | 자동 테스트 완료 |
| Kakao 경로 실패 | `ESTIMATED` 이동시간으로 일정 유지 | 자동·실데이터 확인 |
| Cloud Run 추천 진단 로그 | fetched/candidate/filtered/scheduled/rejected 확인 | 운영 로그 수동 확인 필요 |

2026-09-02 로컬 실측에서는 `locationBasedList2`, `detailCommon2`,
`detailIntro2`, `detailImage2`가 172ms 이내에 응답했다. `searchKeyword2`는
`resultCode=22`, `일일 서비스 요청제한 횟수 초과 에러`가 재현되었다.
따라서 이 시점의 검색 실패는 timeout이 아니라 키 할당량 문제다.

## 5. 실제 서버에서 사용자가 최종 확인할 흐름

테스트 전용 계정과 삭제 가능한 여행을 사용한다.

1. 개인 찜 컬렉션을 만들고 서로 다른 두 경기 지역의 TourAPI 장소를 저장한다.
2. 경기와 여행을 만든 뒤 컬렉션 Import를 호출한다.
3. 여행 후보에는 경기장 지역의 장소만 들어왔는지 확인한다.
4. 후보 하나를 `isRequired=true`로 변경하고 일정을 생성한다.
5. 응답에서 필수 후보, 자동 추천(`addedBy=ALGORITHM`), Anchor, 제외 사유를 확인한다.
6. 자동 추천 하나를 고정하고 재생성한다.
7. 고정 Item은 유지되고 고정하지 않은 자동 추천은 교체되는지 확인한다.
8. 장소 추가, 시간·날짜 변경, 순서 변경, 삭제를 차례로 호출한다.
9. 매 단계마다 일정 상세 조회와 Firestore `itineraryPlans` 문서가 같은지 확인한다.
10. 테스트 여행·컬렉션을 삭제하거나 테스트 데이터임을 표시한다.

Cloud Run 로그에서는 동일 요청 시각과 trace를 기준으로 다음 항목을 확인한다.

```text
recommendation diagnostics
fetchedCount
candidateCount
filteredCounts
scheduledCount
placementRejectedAttempts
Kakao 경로 조회 실패로 예상시간 사용
```

실제 timeout과 호출 제한은 운영 TourAPI를 고의로 과다 호출해 만들지 않는다. 별도 스테이징 환경에서 매우 짧은 timeout 또는 Mock transport를 주입해 확인하는 것이 안전하다.

### 사직 결과 해석

현재 네 지역 품질 감사는 실제 TourAPI 데이터에 직선거리 기반 이동시간을 넣어
알고리즘을 비교한다. 사직의 낮은 삽입 수는 주로 `ROUTE_INEFFICIENT`,
`OUTSIDE_BUSINESS_HOURS`, `NO_AVAILABLE_MEAL_PERIOD`에서 발생했다. 이 결과만으로
전 지역 우회 허용치를 완화하면 다른 지역의 동선 품질이 나빠질 수 있으므로
전역 임계값은 변경하지 않았다. PR 배포 후 실제 Kakao 경로를 사용하는 사직
시나리오를 확인하고 지역 후보 반경 또는 시간대 후보 구성을 조정한다.
